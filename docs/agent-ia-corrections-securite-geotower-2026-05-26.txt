Priorites de correction:

P0 - Proxy SignalQuest abusible via X-Forwarded-For et upload public

Fichiers principaux:
- docs/server/signalquest_proxy.py
- docs/server/main.py
- app/src/main/java/fr/geotower/data/api/SignalQuestApi.kt
- app/src/main/java/fr/geotower/data/workers/SignalQuestUploadWorker.kt

Constat:
- Le rate limit serveur utilise _client_ip(), qui fait confiance directement a l'en-tete x-forwarded-for.
- Un client peut changer x-forwarded-for et contourner le quota IP.
- L'endpoint public d'upload utilise ensuite la cle serveur SignalQuest en Authorization Bearer.
- Risque: abus du proxy, cout backend, spam d'upload, reputation de la cle SignalQuest.

Correction attendue:
- Ne faire confiance a x-forwarded-for que si la requete vient d'un reverse proxy explicitement autorise.
- Ajouter une variable d'environnement de configuration, par exemple TRUSTED_PROXY_IPS, et sinon utiliser request.client.host.
- Nettoyer et tester l'extraction d'IP: IPv4/IPv6, listes x-forwarded-for, valeurs invalides.
- Garder un rate limit par IP robuste et previsible.
- Ajouter une protection applicative supplementaire pour l'upload:
  - option minimale: jeton serveur court signe/HMAC, avec timestamp et expiration;
  - option plus forte: Play Integrity cote serveur avant upload;
  - ne jamais embarquer de secret durable dans l'APK.
- Conserver la validation de taille et mime type image/jpeg.
- Ajouter des tests Python unitaires pour _client_ip ou la nouvelle fonction d'extraction IP.

P1 - Authenticite des donnees telechargees insuffisante

Fichiers principaux:
- app/src/main/java/fr/geotower/data/api/DatabaseDownloader.kt
- app/src/main/java/fr/geotower/data/db/GeoTowerDatabaseValidator.kt
- app/src/main/java/fr/geotower/data/workers/OfflineMapDownloadValidator.kt
- app/src/main/java/fr/geotower/data/workers/MapDownloadWorker.kt
- app/src/main/java/fr/geotower/ui/components/MapDownloadCard.kt
- docs/server/main.py

Constat:
- La base SQLite telechargee est validee structurellement, mais pas signee cryptographiquement.
- Les cartes hors ligne ont un sha256 optionnel; si absent, le fichier est accepte apres controle taille/contenu minimal.
- Risque: en cas de compromission backend/CDN/TLS local, l'app peut accepter des donnees alterees mais structurellement valides.

Correction attendue:
- Ajouter un manifeste signe cote serveur pour la base SQLite et les cartes.
- Embarquer une cle publique dans l'app et verifier signature avant installation.
- Rendre le hash SHA-256 obligatoire pour les cartes.
- Pour la DB, verifier au minimum sha256 obligatoire, puis idealement signature du manifeste.
- Refuser explicitement tout catalogue carte sans hash valide.
- Ajouter/adaptater des tests dans OfflineMapDownloadValidatorTest et autour du parsing DB info si possible.

P1 - Telechargements longs sans plafond dur de bytes

Fichiers principaux:
- app/src/main/java/fr/geotower/data/api/DatabaseDownloader.kt
- app/src/main/java/fr/geotower/data/workers/MapDownloadWorker.kt

Constat:
- Les boucles de telechargement ecrivent jusqu'a fin du flux.
- Si Content-Length est absent ou mensonger, le controle final peut arriver trop tard.
- DatabaseDownloader utilise callTimeout(0) pour le client de telechargement.
- Risque: remplissage disque, blocage long, consommation reseau/batterie.

Correction attendue:
- Ajouter un plafond dur de bytes pendant la copie.
- Pour la DB: utiliser size_bytes du endpoint /api/v2/db/info avec marge stricte.
- Pour les cartes: utiliser estimated_size_mb avec marge stricte ou taille exacte si le catalogue la fournit.
- Rejeter avant telechargement si Content-Length depasse le plafond.
- Rejeter pendant telechargement si bytesCopied depasse le plafond.
- Garder les fichiers temporaires nettoyes en cas d'erreur ou annulation.
- Ajouter tests unitaires sur la validation/plafonds si possible.
