P0 - Manifeste signe pour la DB et les cartes

Objectif:
Empecher l'app d'accepter une DB ou une carte modifiee, meme si le backend, le CDN, ou un TLS local est compromis.

Fichiers probables:
- docs/server/main.py
- app/src/main/java/fr/geotower/data/api/DatabaseDownloader.kt
- app/src/main/java/fr/geotower/data/workers/OfflineMapDownloadValidator.kt
- app/src/main/java/fr/geotower/data/workers/MapDownloadWorker.kt
- app/src/main/java/fr/geotower/data/models/OfflineMapDto.kt
- tests sous app/src/test/java/fr/geotower/data/...

Travail attendu cote serveur:
- Ajouter un endpoint de manifeste officiel, par exemple:
  /api/v2/download/manifest
- Le manifeste doit contenir au minimum:
  - schemaVersion
  - generatedAt
  - expiresAt si possible
  - keyId
  - db:
    - filename
    - url
    - size_bytes
    - sha256
    - schema_version
    - country_code
    - version
  - maps:
    - id
    - map_filename
    - map_url
    - estimated_size_mb
    - sha256
- Signer le payload canonique avec une cle privee Ed25519 cote serveur.
- La cle privee ne doit jamais etre dans le repo ni dans l'app Android.
- Publier une reponse du type:
  {
    "payload": { ... },
    "signature": "base64url...",
    "keyId": "geotower-prod-2026-01"
  }
- La signature doit porter sur le payload canonique, pas sur une chaine JSON construite de maniere fragile.
- Prevoir une politique de rotation via keyId.

Travail attendu cote Android:
- Embarquer uniquement la ou les cles publiques autorisees.
- Verifier la signature du manifeste avant d'utiliser ses champs.
- Refuser tout manifeste:
  - non signe;
  - mal forme;
  - signe avec une cle inconnue;
  - expire;
  - dont schema_version ou country_code ne correspondent pas;
  - dont les hashes manquent ou sont invalides.
- Utiliser les champs verifies du manifeste pour piloter les telechargements DB/cartes.

Tests attendus:
- accepte un manifeste valide signe;
- refuse une signature invalide;
- refuse un keyId inconnu;
- refuse un manifeste expire;
- refuse un hash absent;
- refuse schema_version incorrect;
- refuse country_code incorrect.


P1 - SHA-256 obligatoire partout

Objectif:
Aucune donnee telechargee ne doit etre installee sans hash attendu.

Travail attendu:
- Pour la DB:
  - refuser /api/v2/db/info ou le manifeste si sha256 manque ou est invalide;

  - installer uniquement si le hash correspond exactement.
- Pour les cartes:
  - refuser tout catalogue/manifeste sans sha256 valide;
  - calculer le SHA-256 du fichier temporaire;
  - installer uniquement si le hash correspond exactement.

Tests attendus:

- DB info avec hash invalide refuse;
- carte sans hash refusee;
- carte avec mauvais hash refusee;
- fichier valide accepte.


P1 - Plafonds d'octets pendant telechargement

Objectif:
Eviter remplissage disque, consommation reseau excessive, ou blocage si Content-Length est absent ou mensonger.

Travail attendu:
- DB:
  - utiliser size_bytes du manifeste signe ou de /api/v2/db/info;
  - definir une marge stricte;
  - refuser avant telechargement si Content-Length depasse le plafond;
  - pendant la copie, arreter immediatement si bytesCopied depasse le plafond;
  - supprimer les fichiers temporaires en erreur ou annulation;
  - ne pas utiliser callTimeout(0).
- Cartes:
  - utiliser taille exacte si disponible;
  - sinon utiliser estimated_size_mb avec une marge stricte;
  - appliquer le meme refus avant et pendant la copie.

Tests attendus:
- Content-Length trop grand refuse;
- flux depassant le plafond interrompu;
- fichier temporaire supprime apres erreur;
- progression bornee a 100%.

P2 - Chiffrement local cible

Objectif:
Chiffrer uniquement ce qui peut contenir des donnees utilisateur sensibles. Ne pas chiffrer la grosse DB publique ANFR.

Donnees a evaluer:
- Historique d'upload photo.
- Brouillons d'upload.
- Metadonnees locales de fichiers/photo.
- Preferences sensibles eventuelles.
- Caches lies a localisation ou activite utilisateur.
- Tokens temporaires si l'app en persiste, mais idealement ne pas les persister.

Approche recommandee:
- Utiliser Android Keystore via AndroidX Security / EncryptedSharedPreferences si la dependance est disponible ou acceptable.
- Pour une petite quantite de donnees, preferer un stockage cle-valeur chiffre.
- Pour une vraie DB privee future, evaluer SQLCipher uniquement si le besoin est avere.
- Prevoir une migration douce depuis l'ancien stockage en clair.
- En cas d'indisponibilite Keystore, echouer proprement ou degrader sans crash, mais ne pas stocker de nouveau secret durable en clair.

Tests attendus:
- migration lit l'ancien stockage puis ecrit dans le nouveau stockage chiffre;
- absence de crash si Keystore indisponible;
- tokens expires supprimes;
- aucune nouvelle donnee sensible stockee en clair.
